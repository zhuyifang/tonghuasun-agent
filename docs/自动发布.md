# Agent 与 MCP Apps 自动发布

公开仓库有两条独立发布线：Agent 插件安装包使用 `v<版本>` GitHub Release；MCP Apps 使用经过 Ed25519 签名的 `fqgate/mcp-apps` 稳定目录。它们与 FQGate 主程序分别管理版本，不能把版本号混用。

## 一次性设置

1. 在 Settings → Actions → General 中把 Workflow permissions 设为 `Read and write permissions`，并允许 GitHub Actions 创建 Pull Request。
2. 创建 Environment `agent-production`，设置 required reviewer。它控制 Agent Draft Release 何时正式公开，不需要额外 Token。
3. 创建 Environment `mcp-apps-production`，设置 required reviewer，并添加 secret `FQGATE_MCP_APPS_ED25519_PRIVATE_KEY`。值必须是与 `fqgate/mcp-apps/mcp-apps-ed25519-public.pem` 匹配的 Ed25519 私钥 PEM；不得把私钥写入仓库、日志或构建产物。
4. `main` 必须允许发布工作流在 Release 公开后提交 `update/stable.json`、版本清单和 `.claude-plugin/marketplace.json`。如果分支规则禁止 Actions 直接更新主分支，先按仓库治理要求配置发布自动化写权限，否则稳定通道不会切换。

这里全部使用仓库自己的 `GITHUB_TOKEN`，不需要自建 GitHub App，也不需要跨仓库 PAT。

## 发布 Agent 插件

1. 在 Actions 页面运行“准备 Agent 插件发布”，填写新版本和每行一条的更新说明。
2. 工作流会同步八个适配器、SDK、安装器和文档版本，构建九个确定性插件包，生成 SHA-256 和候选发行清单，然后创建 `release/agent-v<版本>` PR。
3. 检查并合并 PR。主分支会重新构建同一批安装包，并要求每个字节与候选清单一致。
4. 工作流先创建 Draft Release。批准 `agent-production` 后才公开 Release；拿到 GitHub 的真实发布时间后，最后切换稳定清单和 Claude 市场入口。

审批期间 Claude 市场仍指向上一个稳定版，不会提前跳到尚未公开的下载包。已公开 Release 不会被恢复任务覆盖；同版本重跑时会下载远端资产并校验一致性。

## 发布 MCP Apps

1. 在 Actions 页面运行“准备 MCP Apps 发布”，填写 MCP Apps 新版本和最低支持的 FQGate 版本。
2. 批准 `mcp-apps-production` 后，工作流会安装锁定依赖、运行测试、构建 UI、使用正式私钥签名，并立即用仓库中的 FQGate 公钥验签。
3. 工作流创建 `release/mcp-apps-v<版本>` PR。检查清单、签名和文件集合后合并，GitHub 原始文件稳定通道随主分支生效。
4. Gitee 镜像仍需独立同步并验收；GitHub PR 合并不表示 Gitee 已经更新。

## 故障恢复

- Agent Draft Release 阶段失败：修复问题后手工运行“发布 Agent 插件”，填写与 `fqgate/compatibility.json` 一致的版本。
- Agent Release 已公开但稳定清单提交失败：先修复主分支写权限，再用同一版本重跑。脚本只接受内容一致的已公开资产。
- MCP Apps 签名失败：检查 Environment secret 是否为匹配公钥的 PEM，不能改用临时密钥发布。
- PR 分支已存在：先检查是否是同一次发布留下的分支；保留需要的审查记录，处理旧 PR 后再重跑，不要换版本绕过失败。

自动流程只负责 GitHub。现有 Gitee Agent 安装包和 MCP Apps 镜像继续按独立流程同步，确认镜像资产与 GitHub SHA-256 一致后才能对外说明已更新。
